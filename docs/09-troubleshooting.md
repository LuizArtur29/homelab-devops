# Troubleshooting

Este documento registra problemas reais encontrados durante a construção do homelab.

Documentar falhas é importante porque registra não apenas a solução final, mas também o processo de diagnóstico.

---

## Ventoy — Verification Failed 0x1A

### Sintoma

Durante o boot:

```text
Verification failed: (0x1A)
```

### Causa

Secure Boot interferindo com o boot através do Ventoy.

### Solução

Secure Boot foi desativado na BIOS.

Depois disso, o Debian pôde ser iniciado pelo pendrive.

## SSH — Permission denied (publickey)

### Sintoma

```text
Permission denied (publickey)
```

### Diagnóstico

No servidor:

```bash
ls -ld ~/.ssh
ls -l ~/.ssh/authorized_keys
```

Resultado:

```text
No such file or directory
```

### Causa

A chave pública ainda não estava instalada corretamente para o usuário.

### Solução

O diretório `.ssh` e o arquivo `authorized_keys` foram configurados corretamente.

Permissões:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

Depois disso, o login por chave passou a funcionar.

## CGNAT

### Problema

Era necessário permitir que um jogador fora da rede local acessasse o Minecraft.

A conexão residencial não permitia depender de port forwarding convencional.

### Alternativas consideradas

- port forwarding;
- Tailscale;
- túnel público.

Tailscale exigiria instalação de um cliente no dispositivo remoto.

Isso não atendia ao requisito de o outro jogador simplesmente abrir o Minecraft e conectar.

### Solução

playit.gg.

O agente cria um túnel entre o servidor e a infraestrutura pública do playit.

## playit — socket sem permissão

### Sintoma

```text
The playit service is running, but this shell cannot access its IPC socket:

/run/playit/playitd.sock
```

### Causa

O socket estava restrito ao grupo:

```text
playit
```

### Solução

```bash
sudo usermod -aG playit $USER
newgrp playit
```

## playit — agent registration rejected

### Sintoma

Nos logs:

```text
Setup error:
The playit API rejected the agent registration request.
```

### Diagnóstico

```bash
sudo journalctl -u playit -n 50 --no-pager
```

O agente ainda precisava concluir corretamente seu processo de configuração/vinculação.

## playit setup — pkttyagent

### Sintoma

```text
Failed to execute /usr/bin/pkttyagent:
No such file or directory
```

seguido de falha ao iniciar o serviço.

### Contexto

O Debian foi instalado de forma mínima e não possuía alguns componentes normalmente encontrados em instalações desktop.

### Solução

O serviço foi administrado diretamente através do `sudo` e `systemctl`, evitando depender desse mecanismo para iniciar o daemon.

## Minecraft Services indisponível

### Logs

```text
Signed in to signaling service successfully
Waiting for Minecraft services...
Could not connect to Minecraft services.
This is required to accept connections in online mode.
Server stop requested.
```

### Diagnóstico

O servidor estava configurado com:

```text
ONLINE_MODE=true
```

e precisava alcançar os serviços externos do Minecraft.

Foi testada a conectividade geral:

```bash
curl -4 --http1.1 \
  --connect-timeout 10 \
  --max-time 20 \
  -I https://example.com
```

O teste funcionou.

Porém, requisições relacionadas ao Minecraft apresentaram comportamento inconsistente.

Foi então testado:

```bash
getent ahostsv4 \
  net-secondary.web.minecraft-services.net
```

e:

```bash
curl -4 \
  --connect-timeout 10 \
  --max-time 20 \
  -I https://net-secondary.web.minecraft-services.net
```

O endpoint respondeu.

## DNS controlado pelo Tailscale

### Descoberta

Ao verificar:

```bash
cat /etc/resolv.conf
```

foi encontrado:

```text
# resolv.conf(5) file generated by tailscale

nameserver 100.100.100.100
nameserver fd7a:115c:a1e0::53
```

O Tailscale estava controlando o DNS do servidor.

### Solução

O DNS do Tailscale foi desabilitado:

```bash
sudo tailscale set --accept-dns=false
```

Depois disso, o Minecraft foi reiniciado.

### Resultado

Os logs passaram a mostrar:

```text
Server started.
```

e:

```bash
docker ps
```

passou a apresentar:

```text
healthy
```

### Aprendizado

Um problema aparentemente relacionado ao Docker ou ao Minecraft estava, na realidade, relacionado à resolução/conectividade de rede influenciada por outro serviço instalado no host.

Esse incidente demonstrou a importância de testar separadamente:

```text
Aplicação
    ↓
Container
    ↓
DNS
    ↓
Host
    ↓
Rede
    ↓
Serviço externo
```

## SSH — No route to host

### Sintoma

Do CachyOS:

```text
ssh: connect to host 192.168.10.9 port 22:
No route to host
```

Ping:

```text
Destination Host Unreachable
```

### Verificação do servidor

O HP continuava com:

```text
wlo1
192.168.10.9/24
```

e conseguia alcançar o roteador.

### Cliente

O CachyOS possuía Ethernet e Wi-Fi simultaneamente:

```text
enp7s0 -> 192.168.10.33
wlan0  -> 192.168.10.12
```

As rotas foram verificadas com:

```bash
ip route
```

e:

```bash
ip route get 192.168.10.9
```

O kernel selecionava:

```text
enp7s0
```

para alcançar o servidor.

A tabela de vizinhos também foi analisada:

```bash
ip neigh show
```

Posteriormente, o ping voltou a responder:

```text
4 transmitted
4 received
0% packet loss
```

e o acesso SSH voltou a funcionar.

### Resultado

O problema foi transitório na conectividade da LAN e não uma falha persistente do SSH.

```bash

```

```bash
curl -I https://example.com
```

## Principal aprendizado

Troubleshooting deve ser realizado por camadas.

Em vez de alterar várias configurações simultaneamente:

1. reproduzir o erro;
2. consultar logs;
3. identificar a camada afetada;
4. testar uma hipótese;
5. alterar apenas uma variável;
6. testar novamente;
7. documentar o resultado.
